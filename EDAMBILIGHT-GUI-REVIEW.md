## Shell and pages

The shared sidebar is generated by `web/js/navigation.js`. It has a fixed 80px
rail and six destinations: Control, Topology, Devices, Settings, Preview, Help.
The visual system is in `web/css/design-system.css`: dark blue glass panels,
cyan accent, Orbitron headings, Rajdhani body, double panel borders, rounded
cards. `web/css/fonts.css` binds the shipped local font assets. These are usable
reference assets, rather than a reason to create another frontend framework.

| Page | Actual behavior and entry points |
| --- | --- |
| Control (`index.html`, `js/ambilight.js`) | Loads config/devices, renders controls and zones, reads status, applies presets and live config patches. |
| Topology (`topology-editor.html`, `js/topology-editor.js`) | Canvas zone selection, drag, snapping, pan/zoom, rotation, direction, physical length, global center, identify/calibration, explicit Save. |
| Devices (`devices.html`) | Device inventory, topology availability, per-device enable, identify, explicit rescan/reload of the displayed list. |
| Settings (`settings.html`) | OpenRGB endpoint/path/start policy, connection test/reconnect, web port, logs, restart and quit. |
| Preview (`preview.html`) | Standalone WebGL procedural test animations, palettes, effects and playback. It is **not a live view of the captured desktop or LED samples**. |
| Help/loading | Onboarding and initialization status. Loading invokes connection retry; ordinary page connection cancels pending application shutdown. |

## Frontend-to-backend boundary

The original uses Eel: `api(name, ...args)` calls
`await eel[name](...args)()`. Some pages call `eel.method` directly. Merely
replacing the shared `api()` wrapper would leave those direct calls disconnected.
Some callers expect `{ok: ...}`, others `{success: ...}`. Their data and error
contracts must be adapted explicitly; the native plugin is the existing state
and RGB-output owner and must not compete with another sender.

| Operation | Arguments / frontend-consumed result |
| --- | --- |
| `get_ambilight_config` | No args; config including `devices[device_key]`. |
| `set_ambilight_config` | One partial config object; result checked for `ok:false` or `success:false`. |
| `get_ambilight_devices` | Array: `device_key`, `name`, `led_count`, `zone_count`, `has_topology`, `topology_type`, `enabled`. |
| `set_ambilight_device_enabled` | `(device_key, boolean)`; caller restores checkbox on failure. |
| `get_ambilight_device_zones` | `(device_key)`; array: `zone_index`, `name`, `edge`; enable state in config by zone index (legacy name lookup also present). |
| `set_ambilight_zone_enabled` | `(device_key, zone_index, boolean)`. |
| `get_ambilight_status` | `enabled`, `running`, `fps`, `capturer`, `content_rect`, `devices_total`, `active_devices`, `active_zones`, `mapped_devices`, `standby`. |
| `get_scene_topology` | `{success,zones,devices,global_effect_center}`. Scene device records use `device_id`, not the control page's `device_key` name. |
| `reload_scene_from_openrgb` | Same scene shape; zone metadata merged by `(device_id, zone_index)`. |
| `save_scene_topology` | `(zones, effectCenter)`; `{success,message/error}`; only success marks editor saved. |
| `flash_topology_device` | `(device_key/device_id)`; temporary identify operation. |
| `test_topology_calibration` | `(ringMap, calibrationConfig)`; map entries described below. |
| `stop_topology_calibration` | No args; also called on pagehide. |
| `get_settings` / `save_settings` | Settings object / patch. Fields include OpenRGB host/port/path/autostart, web port and help state. |
| `test_openrgb_connection` | `(host, port)`; `{ok,devices,error}`. |
| `reconnect_openrgb`, `retry_openrgb` | Explicit user connection actions. |
| `get_app_version`, `get_init_status` | Version text / initialization status. |
| `cancel_shutdown`, `restart_app`, `quit_app`, `open_log_folder` | Application lifecycle operations, not device mapping. |

Control uses 800ms status polling. It debounces individual slider config writes
by 80ms and sends the final pending value. That is observed original behavior,
not a requirement to introduce sleeps/retries into the native capture path.
Presets batch a config patch after clearing pending per-key writes.

The status UI distinguishes inactive, active, no-devices, no-zones and standby.
It reports a connection problem after failed status reads and clears that banner
after a successful response. Transport failure must not appear as valid empty
inventory, successful Save, or healthy capture.

## Controls and native applicability

The original config offers FPS 1–60, capture selection (auto/WGC/DXGI/mss),
sampling strategy (adaptive+EMA/adaptive/percentile+EMA/percentile80/dominant/mean),
black-bar detection, fixed/adaptive depth, EMA alpha, scene-cut threshold,
saturation boost, luminance floor and standby behavior. Balanced/Cinema/Gaming/
Calm presets set combinations of those options.

Our native backend currently implements GPU regional averaging, 1–30 output
FPS, a 140ms time-based smoother and the required LG wallpaper/app policy.
The original menu labels are not evidence that our backend implements the other
algorithms. Reconstruction must expose functioning controls with truthful units;
do not connect a different setting behind an attractive but inaccurate label.
In particular, an EMA alpha is not interchangeable with milliseconds, and a
DXGI fallback is not a wallpaper-only input behind floating windows.

The original default device list says keyboards are excluded. Our required six
controllers include both matrix keyboards and the mouse, so that filtering and
linear-only geometry cannot be adopted unchanged.

## Topology persistence and geometry

A scene contains `zones`, `devices` and `global_effect_center:{x,y}`. The editor
persists complete zones and the center using the single Save call. Zone fields
consumed by the frontend include:

```json
{
  "device_id": "stable device identity",
  "zone_index": 0,
  "name": "custom zone name",
  "led_count": 10,
  "position": {"x": 5, "y": 5},
  "rotation": 90,
  "direction": "forward",
  "led_spacing": 1,
  "physical_length_cm": null,
  "color": "#14F5FF"
}
```

Scene coordinates are LED/world units, with **Y increasing upward**. Screen Y
is inverted in `worldToScreen`; camera offsets and zoom apply after that. The
original input capture dimensions are not the canvas world dimensions.
Zone keys are composite `(device_id, zone_index)`; list order or names alone
are insufficient. Matrix geometry and device-global LED indexes must survive
any grouping/splitting used for the four monitor edges and two bars.

`physical_length_cm / led_count` sets LED spacing. Rotation and direction have
separate controls. The effect center is stored as percentages within the scene
bounding box. The virtual bounding box expands symmetrically around that center.
Auto Layout stacks device zones; Reset reloads the scene. Unsaved state compares
a snapshot of zones and center, guards navigation, and clears only after a
successful save. Closing Advanced also stops active calibration.

Calibration sends `{device_id:[[hardware_index, ring_index, is_center], ...]}`.
Its hardware index is a cumulative offset over zones sorted by `zone_index`.
The original computes that map in the frontend; copying this assumption into
our system could renumber LEDs when zones are split. The new editor must show
the actual native sample rectangles and preserve their physical LED identities,
with drawing, hit testing and calibration based on the same geometry.

### Reproduced discrepancy in the shipped geometry

The pure-method replay (`geometry-replay.json`) verifies camera transform
round-tripping, then reproduces an inconsistent Y convention:

- For position `(5,5)`, count 4, rotation 0, the hit/bounds rectangle occupies
  Y `4..5`.
- `_ledWorldPos(zone,0)` returns `(5.5,5.5)`, outside that same rectangle.
- `isPointInZone` consequently rejects its own calibration LED center.
- Changing `direction` does not change `buildCalibrationRingMap` output in the
  tested case. This is a frontend observation, not a proven hardware defect.

The replay executes recovered geometry methods only, bypassing construction and
all browser/Eel/device actions. Do not copy that discrepancy into the new map.
This finding does not diagnose the user's current train wallpaper behavior.

## Reconstruction boundary for this system

The existing authorized GUI work remains incomplete. Its next integrated outcome
must provide the recovered Control/Topology/Devices interaction around the one
native lighting owner, with:

- all six actual devices, preserved names and physical LED identities;
- editable mapping, individual sample visibility, rotation/direction and explicit
  Save that updates the native GPU regions and survives restart;
- the selected LG source policy and live capture/output/error diagnostics;
- real output FPS and time-based smoothing controls;
- identify/calibration under exclusive native ownership, with deterministic
  restoration of ambience when the operation ends;
- truthful capture/sample preview, distinct from procedural test animations;
- the supplied review's native capture recovery and timing/error corrections,
  verified at their actual lifecycle boundaries;
- a verified integrated release before claiming that new tooling is usable.

No mapping was changed during this pass. The train observation is preserved
separately and deliberately not pursued further after the user's redirection.
No second original EDAmbilight/BSRGB process or RGB writer was launched. Monthly
upstream maintenance and branch pruning remain in their existing later stage.
